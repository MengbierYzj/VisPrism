# 接口文档（前后端契约）

- Base URL（开发）：`http://127.0.0.1:8000`；前端经 vite 代理 `/api → 127.0.0.1:8000`。
- 所有错误统一结构：`{"error": {"code": <int>, "message": "<string>"}}`。
- 本文档为契约源头：接口路径、方法、字段名、类型、枚举值不得擅自改动；新增字段须向后兼容（可选/默认值）。

## 1. GET /api/health

健康检查。

```json
{ "ok": true, "llm_mode": "mock", "model": null, "prefer_mode": "suggest", "chart_type_prefer_mode": "suggest", "personas": 2 }
```

- `llm_mode`: `"live" | "mock"`——慢道两拍（读图立意/溯源裁决）的实现模式；快道恒为程序化。
- `model`: live 模式下返回模型名，mock 为 null。
- `prefer_mode`: `"suggest" | "apply"`——L2 `prefer` 落地策略（环境变量 `VIZGUIDE_PREFER_MODE`，
  兼容旧名 `VIZGUIDE_CHART_TYPE_PREFER_MODE`）。默认 `suggest`：仅 `prefer: chart.type`
  强制建议，其它可编译 prefer（如 `mark.color`）仍执行；`apply`：所有可编译 prefer 与 set 同权
  （含受控 chart.type → `set_mark_type`）。IBM Recommend 中可映射到 VL mark 的图型
  （bar/line/area/point/arc/rect/tick/boxplot 及 bubble→point、donut→arc+innerRadius、
  heatmap→rect、histogram→bar+bin 等）可执行；radar/wordcloud/treemap/地图/网络等
  仍仅建议。
- `chart_type_prefer_mode`: 与 `prefer_mode` 同值（兼容旧字段）。

## 2. GET /api/personas

机构 persona 列表（内置 `data/*-persona.yaml` + 自定义 `backend/storage/personas/`）。

```json
{ "personas": [ {
  "id": "bbc", "name": "BBC", "full_name": "BBC Visual Journalism",
  "domain": "journalism", "category": "News", "kind": "builtin", "source": "bbc.md",
  "brand_color": "#BB1919", "palette": ["#1380A1", "..."], "abbr": "BBC",
  "layers": { "l1_rules": 12, "l2_adaptations": 8, "l3_philosophy": 4, "l3_stories": 9 },
  "applicability": { "suits": ["..."], "promises": ["..."] }
} ] }
```

- `kind`: `"builtin" | "custom"`。
- `category`（2026-08-10 新增，向后兼容的追加字段）：机构 taxonomy 分类，
  取值 `Government | Education | Non-profit | News | Profit`；自定义 persona
  与无内置提示的机构返回 `Other`。内置八家：cfpb=Government、cmu=Education、
  who=Non-profit、bbc/economist=News、ibm/ebay/shopify=Profit。前端机构选择器
  按此分类做筛选 chips。

## 3. POST /api/personas/parse

上传机构规范 markdown，由 Parser Agent 解析装配为新 persona agent（multipart form）。

| 字段 | 类型 | 说明 |
|---|---|---|
| `file` | file | UTF-8 文本（md/txt），≤512KB |
| `name` | string, 可选 | 机构显示名；缺省取文件名 |

响应：`{ "persona": <PersonaMeta 同上>, "warnings": ["分块解析完成：7 块，L1 10 / L2 23 / L3 12"] }`

- live 模式按带行号的文档块完整解析，不再只读取文档前缀；
- live 单块默认不超过 3000 字符，可通过服务端
  `VIZGUIDE_PARSER_CHUNK_CHARS` 调整；块数会随配置变化；
- 仅真实 `Lx[-Ly]` + 原文 quote 可进入 persona；占位来源或无法核对的证据会被丢弃；
- 三层分类门保证：L1 仅含无条件 must/never 与 design tokens；L2 必须有真实
  `when→then` 情境担保；L3 仅含 philosophy/stories，不携带可执行动作；
- 抽象原则标签会从误标的 L1 重分类为 L3；质量门除规则总数外，至少要求 2 条
  programmatic L1/L2，避免仅返回无 ops 的 suggested persona；
- 对明确的参考型规范条目（语义色、字号、来源、网格、图例、媒介尺寸），Parser
  会补充受控 `when/then`，使其可进入既有快道编译；
- 颜色 token 统一规范化为 `#RRGGBB`；兼容色阶与六位色值连写形式，例如
  `Purple 706929c4` 会解析为 `#6929C4`，原文 evidence quote 保持不变；
- 对原文中的 categorical/qualitative palette 章节，确定性抽取默认色板，并派生
  `color.primary`（首色）与两条 L2：`color_count>=2 → color.range`、
  `color_count<=1 → mark.color`；默认图例方位（top/bottom）在有 default 措辞时
  进入可执行 L1；
- 对齐范例 persona：无条件 should/never 可保留为 L1（llm）；图表推荐章节 → L2
  `prefer: chart.type`；原则行 → L3 philosophy（title+原文 quote）；禁止把
  `706929c4` 一类色阶连写写入 token path；
- 强度关键词按完整词边界匹配（`whenever` 不会误判为 `never`）；仅把整句回填为
  `when.context` 且无可执行 `then` 的项降为 `unmapped`，不装配为无效 L2；
- 质量门要求至少 2 条**可编译出 ops** 的 L1/L2，且至少有一个有证据 token；live
  初检失败时先合并启发式候选补强（`live-augmented`），不再丢弃已成功分块；
- 同证据已有结构化映射时，不再并列返回模型生成的自然语言重复项；需要
  `data_role`/`audience` 但运行事实缺失的规则会进入 `rejected[]`，不得由 LLM
  猜测后执行整图改色；
- 可执行要求按 L1/L2 编译；不满足层级判据的弱指导仍进入
  `unmapped_requirements` 留痕，不会错误装配为 L1；
- 跨多个示例重复出现的颜色模式可以生成带 `derived: true` 和
  `pattern_sources[]` 的 L2 条件规则；单个教程示例进入 L3 `exemplars`，审计副本
  仍进 evidence catalog；
- `parser_provenance` 记录 `llm_chunks_succeeded/failed`；全部 LLM 分块失败但确定性
  规则通过质量门时，mode 为 `deterministic-fallback`，不伪装成 live-chunked；
- **落盘对齐手工范例**：`*-persona.yaml` 仅含 `institution` / `applicability` /
  `L1_signature` / `L2_adaptations` / `L3_narrative`；`parser_provenance`、
  `unmapped_requirements`、`evidence_catalog` 写入同目录 `*-parser-audit.yaml`
  sidecar，不改变 `PersonaMeta` 响应字段。

错误：400（空文件/非 UTF-8）、413（过大）、422（质量门未通过，不注册空壳 persona）。

## 4. POST /api/upload

上传 `vegalite.json`（multipart，字段 `file`，≤2MB）。校验 + 留存 + 事实提取。

```json
{ "file_id": "a1b2c3", "spec": { "...": "..." }, "facts": { "mark_type": "bar", "...": "..." } }
```

错误：400（非法 JSON / 缺少视图定义）、413（过大）。

## 5. POST /api/advisor/run

启动多机构 persona agent 并行咨询（四拍快慢管线）。

Query：`wait`（可选，bool，默认 false）——true 时阻塞至全部 agent 完成（脚本/测试用）。

承接引擎由后端 `VIZGUIDE_ADVISOR_ENGINE` 决定（`v1` 编译执行，默认；`v2` 契约核验，
等价于 §9 `/api/v2/advisor/run`）。两者响应结构一致，本节契约不随切换变化；v2 承接时
`run_id` 带 `v2-` 前缀、`proposal.engine` 为 `advisor-v2`，且不返回 v1 独有的
`llm_execution` 与 `agenda`（前端对二者均按可选处理）。

请求体：

```json
{
  "spec": { "...": "vega-lite spec 对象" },
  "persona_ids": ["bbc", "economist"],
  "context": {
    "medium": "digital",
    "viewport_px": 640,
    "communication_goal": "I want to visualize this huge gap between reported and solved cases beautifully."
  }
}
```

- `context` 可选；`medium` 缺省 `digital`，`viewport_px` 缺省取 spec.width 或 640。
- `context.communication_goal` 可选，字符串，最多保留 2000 字符；表示用户希望读者注意、
  理解或记住的传播/创作意图，也可包含明确的改件请求。后端将其与同一份 `spec` 一起
  输入每个 advisor agent。
- `context.preview_image` 可选覆盖图（向后兼容，**前端无需传**）：缺省由后端
  `vl-convert` 将 advisor 工作副本渲成 PNG 供拍3 多模态 L3 审图。若传入
  `data:image/png;base64,...` 则覆盖服务端渲染。非法或超长时忽略。proposal.facts
  不回传整图，仅可选 `preview_image_meta`（含 `source: server_render|client`）/
  `visual_review`。
- **意图理解（拍1）**：对 `communication_goal` 做结构化归类，写入
  `facts.user_intent_analysis`：
  - `communication`：传播强调/意图 → 回填 `emphasis_target` / `intent`，驱动机构 L2；
  - `edit`：明确改组件（图型/主色/标题/图例等）→ 在 action space + persona 令牌内编译
    ops，`changes[].layer="user"`，拍4优先执行；冲突 L1 `never` 则进入 `rejected`；
    与机构同 action（如双方都 `set_mark_type`）时**用户胜出**，机构项降为 `suggested`
    仍出现在 changes（不因冲突抹掉相关说明）；
  - `mixed`：同时含传播与改件；
  - `other`：仅留痕，不发明 ops。
  不得由模型发明 hex 或未列 action；颜色优先接地机构令牌。
- **Advisor 基础设定（拍1 开头）**：每个 persona 独立写入 `facts.advisor_briefing`
  （机构专家身份、图表叙述、用户目标、L1/L2/L3 摘要），并注入拍1/拍3 与意图分析的
  system prompt；不新增拓扑拍次。
- **配色原则（facts，向后兼容）**：拍1 写入 `coloring_mode`
  （`uniform` | `paired` | `categorical` | `highlight`）。拍2/3 按该模式落实机构色板
  **分配原则**（序列/角色），而非仅检查「颜色是否落在色板内」；相关 change 可能为
  `d-color-assignment` 或带 `color_alternatives` 的配色项。不新增请求字段。
- **Decision IR（facts，向后兼容可选）**：`facts.chart_slice`（紧凑图摘要，含
  `color_structure` / `category_samples` / `series_samples`）、
  `facts.decision_ir`（读图决策：intent/coloring_mode/organization 等）、
  `facts.organization`；强调绑定可选字段 `emphasis_field`、
  `emphasis_mechanism`（`series_scale`|`literal_condition`|`category_condition`）。
  拍1/3 live 用 slice 做理解与裁决；拍4 按 mechanism 编译安全 ops（LLM 不写 VL）。
  `invariants` 可含 `d-coloring-mode`。不新增请求字段。
- **复合图层识别（facts，向后兼容可选字段）**：`has_drawn_grid`、`drawn_grid_color`、
  `title_from_text_layer`、`unit_count`、`primary_unit_index`、`layer_roles`、
  `chrome_layers`。主几何优先 area/line/bar；改色写 fill/stroke。
- **拍前抽组件重建**：live 时先 LLM 裁决层角色，再 extract→emit；**尽量保留图层**
  （annotation/grid/中心标注等），仅自绘假轴 `drawn_axis` 默认丢弃；title/source 提升到根。
  `facts.spec_rebuild` 含 `role_source` / `role_overrides`；若有改动，proposal 可含
  `prepared_spec`（四拍实际基线）。`original_spec` 仍为上传原稿；`modified_spec` 在
  prepared 基线上套用 persona ops（非对导出器绝对布局原地打补丁）。
- 兼容旧客户端传入 `context.user_intent`；后端会归一化为 `communication_goal`。新客户端
  应只发送 `communication_goal`。

响应（启动即返回；`wait=true` 时 agents 已含完整 proposal）：

```json
{
  "run_id": "20260802-0024",
  "status": "running",
  "created_at": "2026-08-02T00:24:00+08:00",
  "llm_execution": {
    "outcome": "live_pending",
    "configured_mode": "live",
    "model": "gpt-4o-mini",
    "api_calls": { "total": 0, "successful": 0, "failed": 0 },
    "real_llm_succeeded": false,
    "llm_api_mock_fallback": false,
    "summary": "live 已配置，正在等待真实 LLM 调用结果",
    "agents": []
  },
  "agenda": null,
  "agents": [ { "persona_id": "bbc", "status": "pending", "progress": 0.05, "proposal": null, "error": null } ]
}
```

- `run_id`：本地时间精确到分钟，格式 `YYYYMMDD-HHMM`；同一分钟内再次启动时追加
  `-2`、`-3`…。快照与 LLM 日志同名落盘：`storage/runs/{run_id}.json`、
  `{run_id}.llm.jsonl`。
- `llm_execution`：本次运行的 LLM 执行证据（不含 prompt、模型原文响应或密钥）。轮询时会
  实时更新；`outcome` 为 `mock_configured | live_pending | live_succeeded | live_fallback |
  live_no_success`。只有 `real_llm_succeeded=true` 且 `api_calls.successful>0` 才能确认至少
  一次真实 LLM 响应已成功解析；`live_fallback` 表示 live 调用失败并已改用启发式。
  `mock_configured` 表示本次由配置直接使用 mock，而非 API 故障导致的回退。
- `agenda`（可选，向后兼容，可为 null）：**主持人议程合成**。live 运行在全部 agent
  完成后、`status` 变为 `done` 之前，由一次 LLM 调用（LEAD 主持人视角）把跨机构
  changes 组织成自然叙事议程；mock 配置或合成/校验失败时为 null，前端回落本地
  确定性派生（按 change 类别分组）。结构：

```json
{
  "issues": [ {
    "title": "Categorical rainbow doesn't serve the goal",
    "blurb": "Four hues encode product, but the goal is a single comparison…",
    "category": "color",
    "discussion_intro": "Both advisors flag the categorical palette; BBC mutes the context…",
    "quick_asks": ["What about colour-blind readers?"],
    "treatments": [
      { "persona_id": "bbc", "line": "Single accent on the leader; context muted to grey",
        "why": "When one value carries the story, colour only that value and let the rest recede",
        "change_ids": ["bbc:a-color-two"] }
    ]
  } ]
}
```

  - `category`：`title|color|labels|axes|layout|typography|other`（前端锚点定位，
    与本地派生的设计对象词汇表一致）。
  - `treatments[].change_ids` 经后端快道验证：id 必须真实存在且属于该机构，全局
    不重复；同机构在同一议题下多条 treatment 已合并为一行。漏网 changes 先按
    关键词救援进同类议题（行文退化为 change label），仍无归属者进入标题为
    `Smaller refinements from the guides` 的兜底议题——每条修改始终有采纳入口。
  - `treatments[].why`：机构决策的规范依据行，按驱动规则的层统一句式——L2
    条件规则严格 "When {situation}, {approach}"（situation 来自规则 `when` 条件），
    L1 签名规则陈述馆规（"House norm: …"），L3 哲学推导引原则（"From '…': …"）。
    救援/兜底 treatment 的 `why` 为空串，前端回落该机构 reason 首句。
  - 叙事文本经程序校验：数据型数字（>24 或带百分号）必须在图表事实池内，否则
    该字段降级（标题不接地则整个议题弃用）；hex 色码统一转为口语色词
    （色板 swatch 由前端效果行渲染）。

错误：400（spec 非法 / persona_ids 空）、404（未知 persona）。

## 6. GET /api/advisor/run/{run_id}

轮询运行状态。结构同上；`status`: `"running" | "done"`。

该端点同时查询 v1 与 v2 两个 run 存储，因此切换 `VIZGUIDE_ADVISOR_ENGINE` 后，
仍在内存中的旧 run_id 依然可以正常轮询。

- agent `status` 枚举（四拍阶段）：`pending | reading | detecting | adjudicating | compiling | done | error`；
  `progress`: 0.05/0.2/0.45/0.7/0.9/1.0 对应映射。
- agent 完成后 `proposal` 字段：

```json
{
  "persona_id": "bbc", "persona_name": "BBC",
  "facts": { "mark_type": "bar", "series_count": 1, "data_topic": "business",
             "intent": "comparison", "emphasis_target": "C产品",
             "has_drawn_grid": false, "title_from_text_layer": false,
             "layer_roles": [], "...": "..." },
  "original_spec": {}, "modified_spec": {},
  "changes": [ {
    "id": "bbc:a-color-highlight", "rule_id": "a-color-highlight",
    "label": "Orange highlight",
    "reason": "BBC Blue + BBC Orange for contrast…（src: L42）",
    "prompt": "Highlight 'C产品' in #FAAB18 and render the rest in the base color.",
    "layer": "L2", "strength": "should",
    "confidence": "medium", "status": "applied",
    "warrant": { "src": ["L42"], "story_id": "n-contrast", "story": "…",
                 "quote": "", "source_file": "bbc.md", "derived": false },
    "ops": [ { "action": "highlight_category", "field": "product", "value": "C产品",
               "color": "#FAAB18", "base_color": null } ]
  } ],
  "rejected": [ { "rule_id": "s-whitespace", "layer": "L1", "label": "Generous whitespace",
                  "reason": "…驳回留痕", "src": ["L73"] } ],
  "invariants": [ { "rule_id": "s-accessibility", "ok": true, "detail": "…",
                    "initially_violated": true, "resolved_by_compile": true } ],
  "trace": [ { "beat": 1, "lane": "slow", "name": "读图立意", "ms": 0.2, "summary": "…", "mode": "mock" } ],
  "summary": "7 applied, 0 suggested, 5 rejected",
  "elapsed_ms": 1207.8
}
```

字段枚举：

- `changes[].layer`: `"L1" | "L2" | "L3-derived" | "user"`；`status`: `"applied" | "suggested"`；
  `confidence`: `"high" | "medium" | "low"`。
  **v2 引擎溯源（2026-08-15 起）**：`layer`/`strength` 不再恒为 `L3-derived`/`should`。
  当改动引用到该 persona 知识库中的真实规则 id 时，按规则声明的层级与强度记录
  （`rules`→L1、`adaptations`→L2、`philosophy`→L3），并回填 `warrant.src` 与
  `warrant.source_file`；引用不到任何成文规则时仍记为 `L3-derived` 且
  `warrant.derived=true`。取值域与字段名不变，前端无需改动。
  **`applied` 语义（收紧、向后兼容）**：仅当该 change 的 ops 已写入 working spec（相对执行前
  有实际 diff）才为 `applied`；无落点、已是目标态、或同节点被更高优先级决策覆盖时为
  `suggested`（reason 会注明）。拍4 机构同节点合并：慢道采纳优先于快道候选。
- `ops[].action`: `set_mark_type | set_mark_color | remove_encoding_channel | set_color_range |
  highlight_category | set_legend | merge_config | set_size | set_background |
  set_title_anchor | set_title_text | set_subtitle | set_font | set_font_sizes |
  sort_categories | set_orientation | add_value_labels | remove_value_labels | direct_label |
  set_axis_zero | set_grid_style | set_band_padding | set_axis | thin_axis_labels |
  set_mark_style | set_text_style | set_source_note`（2026-08-08 起新增布局类动作，均为
  向后兼容的追加；未识别 action 前端按通用效果行渲染）。
- 布局类动作语义：`sort_categories`（类别轴按值排序，`order: asc|desc`）、
  `set_orientation`（竖条转横条，x/y 编码互换、sort 引用翻转）、`add_value_labels`
  （单系列 bar 追加数值标注 text 层）、`direct_label`（冗余图例摘除；多系列 line 加线端
  系列名并置 `legend: null`）、`set_axis_zero`（数值通道 `scale.zero=true`）、
  `set_grid_style`（网格 `dotted|dashed|solid` + 可选 `opacity`/`color`）、
  `set_band_padding`（类别 band 的 `paddingInner/Outer`，柱宽-间隙节奏）。
- `set_mark_type` 可由：(1) persona 显式 `set/override: chart.type`；(2) 用户意图分析归为
  `edit` 且图型受控时（`layer=user`，必要时 `rebuild_unit`）；(3) 当
  `VIZGUIDE_PREFER_MODE=apply` 时，L2 `prefer: chart.type` 对受控 mark 同样落地。
  有类别/数值字段时对复合 layer 执行 `rebuild_unit`。默认 `suggest` 下 `prefer: chart.type`
  仍仅作建议；其它可编译 prefer 不受此限。语义图型别名示例：`pie`/`donut` → `arc`
  （donut 带 `innerRadius`）；`bubble`/`scattorplot` → `point`；`heatmap` → `rect`；
  `lollipop` → `tick`；`histogram` → `bar`+bin；`stacked bar|area`/`stream` → `bar`/`area`。
- `set_font`/`set_font_sizes` 会剥除 encoding 通道上的字体字号（避免盖住 config），并同步根
  `title` 与自绘标题 text 层。`set_title_text` 用于 sentence case / 标题精简等 L1 文案落地。
- `suggested` = 条件成立但超出单图 spec 自动执行范围（版式/无 VL mark 的图型）、需人工
  核对、无 ops、执行无 diff、或同节点被覆盖；Composer 对无可写入 ops 记 `skipped`。

## 7. POST /api/design/apply

跨机构采纳合成：

- v2 + live：把被采纳 change 当作设计契约，LLM 重构一份完整 Vega-Lite；随后程序
  核验主数据逐字保真、每条决策的最终实现路径与 scope 一致，并用 vl-convert 做
  真实编译/渲染检查；视觉模型可用时再做最终成图验收。任一硬核验失败则自动回退
  到确定性槽位投影，不交付未经验证的模型输出。
- v2 + mock/LLM 失败：保留原有 `compose_component` 精确路径投影作为可用性降级。
- v1：继续确定性重放受控 ops；自由文本指令仅 live 模式生效。

请求体：

```json
{
  "spec": { "...": "原始 spec" },
  "changes": [ { "id": "bbc:a-color-highlight", "ops": [ { "...": "..." } ] } ],
  "instructions": "（可选）用户对最终组合的额外指令",
  "context": { "communication_goal": "用户最初的传播目标" }
}
```

- `changes[]` 直接回传 run 响应中的 change 对象（至少含 `id` 与 `ops`）。
- v2 引擎的 change 使用 `ops[].action = "compose_component"`（带 `component`、
  `candidate_spec`、`spec_paths`、`removed_paths`），并可带
  `contract={verified,source,scope,actual_paths,set_paths,removed_paths,
  compatible_scopes,verification_errors}`。`actual_paths` 是完整证据清单；`set_paths` 与
  `removed_paths` 区分赋值和删除语义。一个路径可以属于多个 component，例如
  `title.subtitleColor → [color,title]`、`axis.gridColor → [axes,color]`。
  比例尺按所属 channel 判定：`encoding.strokeDash.scale.range → [color]`，而
  `encoding.y.scale.domain → [axes]`，不会因为路径中出现 `scale` 就一律判为 Axes。
  live Composer 不假设这些路径能跨树移植，而把它们连同
  完整机构候选图作为改动证据；最终 `implementation[].realized_paths` 是重构后新树
  上的实际落点。新建 layer 内的颜色叶节点会作为 `evidence_paths` 证明 Color 声明，
  明确声明且被父级原子 Structure diff 覆盖的嵌套叶路径也会生成 evidence-only 精确证据，
  但不会脱离其结构依赖做确定性叶节点投影；mock/失败降级仅执行可移植的 set/remove 路径。
  scope 归属除静态路径外还可读取 containing mark：例如 text mark 的
  `encoding.y.value` 同时可属于 Axes 和 Labels。
  Advisor manifest 与 Proposal contract 使用同一共享分类器；text mark 的 `mark.type`、
  `dx/dy`、annotation transform 和位置 encoding 可归 Labels，但其中 font/color 仍分别归
  Typography/Color。`padding.top`、`autosize.type` 等子属性归 Layout。
- `context.communication_goal` 应沿用 advisor run 的同一传播目标，避免终稿丢失任务语境。
- v1 的 `set_mark_color` 等动词行为不变。

响应：

```json
{
  "final_spec": { "...": "..." },
  "applied": ["bbc:a-color-highlight"],
  "skipped": [ { "id": "economist:a-grid-narrow", "reason": "建议类修改（无可执行 ops）…" } ],
  "conflicts": [
    {
      "node": "mark.color",
      "winner_persona_id": "bbc",
      "winner_change_id": "bbc:a-color-single",
      "winner_label": "House blue series",
      "loser_persona_id": "economist",
      "loser_change_id": "economist:s-palette-blues",
      "loser_label": "Navy palette",
      "winner_effect": "#1380A1",
      "loser_effect": "#141F52",
      "reason": "修改冲突（节点 mark.color）：economist 与 bbc 意见不一致，已采用采纳项更多的 bbc（3 项 vs 2 项）"
    }
  ],
  "notes": ["Composer 已根据采纳的设计契约重构完整 Vega-Lite，并完成数据、决策路径与渲染核验"],
  "composition": {
    "mode": "llm_reconstruction",
    "llm_called": true,
    "decision_count": 3,
    "realized_count": 3,
    "implementation": [
      { "change_id": "bbc:a-color-highlight", "realized_paths": ["/layer/1/encoding/color/condition"] }
    ],
    "render": { "ok": true, "width": 780, "height": 520 },
    "visual_review": { "verdict": "pass", "findings": [] }
  }
}
```

- `conflicts[]`：跨机构对同一 spec 节点（如 `mark.color`、`background`）修改不一致时的消解记录；胜出方为用户本次采纳项更多的 persona，落败修改的 ops 不写入 `final_spec` 并进入 `skipped`。
- `composition.mode`：`llm_reconstruction` / `deterministic_projection` /
  `deterministic_ops` / `deterministic_fallback`。前端据此明确显示当前终稿是否经过
  LLM 全量重构，以及多少条选择已在最终代码中找到可核验落点。

## 8. POST /api/advisor/discuss

Review Board 议题讨论：用户对某个议题向相关机构 persona 追问，机构以第一人称回答并
逐字引用指南 warrant；≥2 机构对议题有立场时，主持人（LEAD）补一条合成建议。
回复是**文字层**：不产生新 ops，采纳仍走 run 响应中的 changes + `/api/design/apply`。

请求体：

```json
{
  "spec": { "...": "原始 vega-lite spec" },
  "persona_ids": ["bbc", "economist"],
  "issue": {
    "key": "color",
    "label": "Color & emphasis",
    "changes": [ { "id": "bbc:a-color-highlight", "label": "Orange highlight",
                   "reason": "…", "status": "applied", "layer": "L2",
                   "confidence": "medium", "warrant": { "...": "..." },
                   "ops": [ { "...": "..." } ] } ]
  },
  "question": "Why does this matter for my chart?",
  "history": [ { "role": "user", "text": "…" }, { "role": "bbc", "text": "…" } ],
  "context": { "communication_goal": "（可选）与 run 相同的用户传播目标" }
}
```

- `issue.changes[]`：直接回传 run 响应中该议题聚合的 change 对象（跨机构混合；后端按
  `id` 前缀 `{persona_id}:` 归属机构）。前端的议题聚合方式不影响契约。
- `question`：必填非空，≤2000 字符。`history` 可选（`role` 为 `user` / `moderator` /
  persona_id），后端仅保留最近 8 条。
- mock 模式：确定性模板回复，内容与引用全部来自 `issue.changes` 的 reason/warrant；
  live 模式：逐 persona 一次受机构 briefing 约束的 LLM 调用，citations 经程序校验必须
  逐字命中提供的 warrant，失败自动降级模板（`outcome: "live_fallback"`）。

响应：

```json
{
  "issue_key": "color",
  "replies": [
    {
      "persona_id": "bbc",
      "persona_name": "BBC",
      "text": "Colour should serve the story…",
      "citations": [ { "quote": "Use one strong colour…", "src": ["L42"], "source_file": "bbc.md" } ]
    }
  ],
  "synthesis": { "text": "BBC and The Economist agree…" },
  "conflict_nodes": ["mark.color"],
  "llm_mode": "mock",
  "outcome": "mock"
}
```

- `replies[]`：与请求 `persona_ids` 同序；议题中无该机构 changes 时返回中立回复且
  `citations` 为空。
- `synthesis`：仅当 ≥2 机构对议题有立场时非 null；单机构议题为 null。
- `outcome`: `"live" | "live_fallback" | "mock"`。

错误：400（spec 非法 / question 为空或超长）、404（未知 persona）。

## 9. POST /api/v2/advisor/run（实验性：契约式引擎）

与 §5 并行的第二条咨询管线。请求体、Query 参数（`wait`）与响应外层结构
（`run_id` / `status` / `agents`）**与 §5 完全一致**，前端可复用同一套类型与
§6 的轮询端点形态；差别只在 agent 内部如何产出提案。

两者的取舍：

| | §5 `/api/advisor/run` | §9 `/api/v2/advisor/run` |
|---|---|---|
| 拍3 产物 | 慢道裁决结论（程序据此编译 ops） | LLM 直接返回完整 Vega-Lite |
| 可改动范围 | 受控动作词汇表（约 30 个动词） | Vega-Lite 全部合法结构 |
| 拍4 职责 | 编译执行 + L1 不变量核验 | 安全闸门 + L1 不变量核验 + 归因核验 |

v2 特有的 agent 字段（均为**新增可选**，不影响既有解析）：

- `proposal.changes[].component_detail`：`{ before, after, spec_paths[], execution }`，
  其中 `spec_paths` 为该组件在候选 spec 中的叶子 JSON Pointer；
- `proposal.changes[].problem` / `problem_evidence` / `severity`（可选，2026-08-15 起）：
  该条改动**回应的视觉审阅结论**——分别是问题描述、图上实测到的证据与严重度。
  改动用 `rule_id` 引用结论（`acceptance_findings[2]`，亦兼容 `AF-3` 等简写，简写按
  1 起计且越界不解析）；引用的是机构规则或未具名清单时三者缺省，界面据此如实
  区分「有审阅结论支撑」与「无」；
- `proposal.changes[].warrant.quote`（2026-08-15 起不再恒空）：引用到机构成文规则
  时为**条文原句**，`warrant.src` 同时给出它在原始指南中的位置（如 `L204-238`）。
  注意 `warrant.story` 存的是叙事正文（此前误传叙事编号如 `n-hierarchy`）；
  `warrant.derived=false` 才表示确有成文规则可引，前端据此区分「馆规」与「推导」；
- `proposal.changes[].knowledge` / `knowledge_layers`（可选，2026-08-15 起）：该条
  改动兑现的机构知识。`knowledge` 是主层，`knowledge_layers` 列出同时兑现的各层
  （一条改动可以同时有 L1 Traits、L2 Adaptations、L3 Identity）。形如
  `{ layer, applied?, tokens?, rule?, condition?, philosophy?, quote?, title? }`：
  - `layer="L1"` 带 `applied`（落到图上的具体令牌，如 `"Title color #1A1A1A; subtitle color #595959"`）
    和/或 `tokens`（能回认的命名色板）和/或 `rule`（条文原句）。色值、字号属于
    `doc/研究问题.md` §L1 的 Color / Typography，优先于哲学标签；
  - `layer="L2"` 带 `condition`——触发该适应的条件，已念成从句
    （`"the goal is to highlight the key message"`、`"the canvas is more than 600px wide"`），
    对应研究问题 §L2 的 Data / Intent / Audience；
  - `layer="L3"` 带 `philosophy`——该机构宣示过的设计哲学关键词，取自
    `doc/研究问题.md` §L3 的六词表（clarity / accuracy / integrity / narrativity /
    accessibility / effectiveness）。
  归因依据是 `facts.layer_implementation` 里的 spec 路径证据；无证据可依时整个
  字段缺省，**不做推测**。受此归因影响，`changes[].layer` 现在可能取到 `L2`
  （枚举本就包含，此前实际从未出现）；
- `proposal.facts.layer_implementation` / `goal_implementation`：L1/L2/L3 与用户
  传播目标的兑现自评（含 `status: implemented|unmet|inapplicable`）。其中
  `l2[].spec_evidence` 里的 JSON Pointer 会被用来把改动归因到对应层级，
  因此该字段**应当逐条给出落点路径**；
- `proposal.facts.visual_review`：视觉审阅、布局修复与验收闸门留痕；
  验收因渲染取不到而跳过时，`acceptance.render` 会带上渲染器的失败原因，
  用于区分「候选图真坏」与「渲染器抖动」；
- `proposal.facts.structural_repairs`（可选，2026-08-15 起）：编译前由程序做的
  确定性代码/版式纠错清单（剥离协议键、为缺 `type` 的 `x2/y2` 补类型、把宽于
  绘图区的长标题折行；把被误写成像素常量的位置常量按 `datum` 读回）。这些改动
  署名给程序，不计入 persona 的设计决策；
- `proposal.changes[].ops[].candidate_spec`（v2）：其中主数据表以
  `{"$ref": "__vizguide_primary_data__"}` 占位，§7 组装时按请求 `spec` 逐字还原。
  这是传输层压缩，避免同一张数据表在一个 persona 的十几条卡片里重复序列化；
  前端不读该字段，原样回传即可；
- 引擎内部审计经 `beats.beat4.l1_contract_verification` 暴露：
  `{ ran, mode, before[], patched[], patch_rejected[], after[], unmet[] }`。
  `before`/`after` 是同一批 L1 检测器在**生成图**上的核验结果，
  `patched` 为快道用令牌 ops 确定性修补的规则 id。

安全边界（拍4 拒绝候选的条件）：原始主数据表被篡改、受保护静态文案在未声明
`text_changes` 的情况下丢失、Vega-Lite 编译/运行失败、渲染出单色空画布，或实际
画布小于任一显式声明 view 尺寸的一半（典型为 Vega 运行异常后只返回标题残片）。
任一代码/渲染安全条件命中时，`delivery_state="needs_vega_lite_repair"`，但候选图及其
组件说明仍保留在 Gallery，供用户查看和后续修复；相关 change 会标记
`execution="requires_vega_lite_repair"`。最终视觉验收及一次自动返工属于建议性质量记录：
即使仍返回 `accepted=false`，系统也交付当前得分最高的有效候选，并在
`facts.visual_review.delivered_despite_visual_rejection=true` 留痕，不再显示整张质量门拒绝卡。

`changes[].contract.verified=false` 的旧记录/回放项在前端显示 `Unverified` 且按钮禁用；
`POST /api/design/apply` 也会再次过滤并写入 `skipped`，不能经构造请求绕过。

错误：400（spec 非法 / persona_ids 为空）、404（未知 persona）。

## 10. 历史 run 的留痕与回放

每次 run 结束后自动落盘两个文件到 `backend/storage/runs/`，无需额外操作：

- `{run_id}.json`：完整快照，含 `request`（spec / persona_ids / context）与各 agent
  的完整 proposal（`modified_spec`、`changes`、`rejected`、`invariants`、`trace`、`facts`）；
- `{run_id}.llm.jsonl`：该 run 每一次 LLM 往返的 system / user / raw / parsed 留痕。

v1 与 v2 的快照结构一致，故以下端点对两个引擎的记录都适用。

### 10.1 GET /api/v2/advisor/runs

列出全部可回放记录（按修改时间倒序）：

```json
{ "runs": [ {
  "run_id": "v2-20260814-2142", "engine": "advisor-v2", "status": "done",
  "created_at": "2026-08-14T13:42:11+00:00",
  "persona_ids": ["bbc"], "replayable_persona_ids": ["bbc"],
  "chart_title": "Reported cases by city", "communication_goal": "show the gap",
  "file": "v2-20260814-2142.json", "size_bytes": 33576
} ] }
```

### 10.2 GET /api/v2/advisor/runs/{run_id}

取回该记录的完整快照原文，供离线分析与论文取证。错误：404（未找到 / 无法解析）。

### 10.3 POST /api/v2/advisor/replay

按 run_id **精确**复现一次历史咨询。回放不调用 LLM、不重新推理，逐字重放已存提案，
并按 `reading → detecting → adjudicating → compiling` 四拍推进状态，因此前端可用
与 §6 相同的轮询方式呈现。

Query：`wait`（可选，bool，默认 false）。

```json
{ "run_id": "v2-20260814-2142", "persona_ids": ["bbc"], "beat_delay_ms": 0 }
```

- `persona_ids` 可选；缺省回放记录中全部有提案的机构，显式传入则只回放子集
  （便于在同一条记录上单独回看某个机构）。
- `beat_delay_ms` 可选，每拍停留毫秒数；缺省取 `VIZGUIDE_REPLAY_BEAT_DELAY_MS`（350），
  脚本与测试可设 0。

响应结构与 §5/§9 相同，回放 run 额外带三个字段（2026-08-15 起）：

- `replay_of`：被回放的原始 run_id；
- `spec`：当初那张原图。前端复现时手里没有它，若不随 payload 带出就得为取一个
  spec 而下载整份快照（实测 2.7 MB）；
- `context`：当初的请求语境（如 `communication_goal`）。

三者**只出现在回放 run 上**，一次真实咨询的 payload 不含它们，前端据 `replay_of`
分辨两者。回放 run 的 `run_id` 形如 `replay-{原始id}-{时分秒}`。**回放是只读的**：
不覆盖也不新增快照文件。

回放 run 与真实 run 同住 v2 存储，而 `GET /api/advisor/run/{run_id}`（§5）本就
两个存储都查，因此**回放可以直接复用前端既有的轮询链路**，无需另设端点。

> 前端入口：以 `?replay=<run_id>` 打开页面即自动复现，`&pace=<毫秒>` 覆盖每拍
> 停留时间。注意前端轮询间隔为 650ms，而 `beat_delay_ms` 默认 350ms，此时界面会
> 整拍漏掉「裁决」；要让四拍都可见需设到 650ms 以上（建议 1500）。

错误：404（未找到记录 / 记录无可回放提案）、400（run_id 非法或含路径分隔符 /
记录缺少所请求机构的提案）。

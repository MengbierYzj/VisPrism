# 后端方案：机构设计人格多智能体架构

> 对应研究方法（`doc/研究问题.md`）：表示 = Institutional Design Persona（McAdams 三层）；
> 推理 = Fast–Slow Norm Execution（慢-快-慢-快四拍）。
> API 契约见 `doc/api/接口文档.md`。

## 1. 多智能体架构选型

**纯自定义框架（Python + asyncio），不依赖 LangGraph / AutoGen / CrewAI。**

架构原则：**同构管线、异构知识（homogeneous pipeline, heterogeneous knowledge）**

- 每个机构 agent = 同一条四拍推理引擎 + 各自的 persona 知识（L1/L2/L3）。
  agent 不是一个类的六个子类，而是同一引擎被不同 persona 参数化的实例。
- 机构 agent 之间**无通信、无协商**：研究设定是"多机构独立提案、用户跨机构组合"，
  并行扇出（asyncio.gather）即可，agent 编排不构成额外复杂度。
- 不用现成多智能体框架的理由：
  1. 研究贡献在"表示如何编译为可执行知识、推理如何按快慢路由"，路由必须是
     显式、可审计的状态机，才能在论文中刻画并做消融；
  2. 快道（拍2/拍4）是纯确定性代码而非 LLM 调用，现成框架围绕 LLM 调用图设计，
     硬套会把方法埋进框架抽象；
  3. 逐拍 trace / provenance 是一等输出，自持实现最直接。

系统内共三类智能体角色：

| 角色 | 职责 | 实现 |
|---|---|---|
| Persona Advisor Agent × N | 对输入图表按机构人格走四拍推理，产出修改方案 | `app/core/runner.py` + `app/core/beats.py` |
| Parser Agent | 机构规范 md → persona.yaml（三层编码），装配新 advisor | `app/core/parser_agent.py` |
| Composer | 用户跨机构采纳的修改 → 确定性合成终稿（+ 对话式微调） | `app/core/composer.py` |

### Parser Agent 的三层映射与可追溯性

长规范不再截取固定前缀，而是按带全局行号的文档块逐块抽取，再由程序统一校验、
去重和装配：

- live 抽取的单块默认限制为 3000 字符，并可通过 `VIZGUIDE_PARSER_CHUNK_CHARS`
  调整，以避免 OpenAI 兼容网关对长输入/长 JSON 生成触发硬超时；
- **L1（气质签名）**：只接收无条件、跨情境恒定的 must/never 规则，以及命名色板、
  CSS 变量和语义 design token 树；能映射到受控动作的规则携带结构化 `then` 并走快道；
- **L2（特征适应）**：必须有原文担保的任务/数据/图型/主题/媒介/受众条件；
  结构化 `when→then` 可快判，未能结构化的动作以自然语言保留并交慢道裁决；
- **L3（叙事认同）**：原则宣言进入 philosophy，设计理由进入 stories，且不携带
  `when/then` 参数；教程示例进入 `evidence_catalog.examples`，不擅自提升为机构规范。
- 对“设计标准参考”型短文档（语义色名、字号条目、简短规则清单），程序会从明确的
  角色/数值/动作措辞补充结构化 token 与 `then`：单/双/多序列配色、字体字号、来源、
  网格、图例、数字媒介尺寸均可进入快道，而非退化为无 ops 的 suggested。
- 颜色 token 在证据校验前统一规范化为 `#RRGGBB`；兼容将色阶与六位色值连写的形式
  （如 `Purple 706929c4` 表示色阶 70、色值 `#6929C4`），同时保留未改写的逐字
  evidence quote 以供溯源。
- 对指南中的 categorical/qualitative palette 章节做机构无关的确定性抽取：生成
  `palette.categorical`、派生 `color.primary`，并分别编译多色/单色两条可执行 L2；
  质量门以“能否 compile / 受控 prefer chart.type”计数（与 `prefer_mode` 解耦），
  live 失败时合并启发式补强而非整篇回退抹掉已成功分块；整句回填的假
  `when.context` 不得升格为 L2。
- **live 以 LLM 理解为主**：分块抽取后增加整编步（去重、重分类、图型散文→
  `prefer chart.type`）；程序只做证据校验与三层门。叙事型 HIG（如 Apple）可无
  hex 令牌——在已有 ≥2 条可执行 L1/L2 时令牌缺失仅警告。
- 对齐手工范例（bbc/economist-persona）的归纳标准：无条件 should/never 可保留为
  L1（check:llm）；图型推荐（含 Marks 散文）编译为 L2 `prefer: chart.type`；
  Design principle 行进入 L3 philosophy；色值 token path 禁止写入色阶+hex 原串。

装配阶段设置程序化“三层分类门”，不直接信任 LLM 给出的层级：含条件的 L1 会被
重分类为 L2；无真实条件担保的 L2、无条件但不够强的弱指导进入
`unmapped_requirements`；示例主题条件进入 evidence catalog / L3 `exemplars`。
`when.intent` 允许近义短语接地（compare→comparison）。对于 cookbook 中未显式
命名、但跨多个机构示例反复出现的颜色模式，可生成 `derived: true` 的 L2 候选。

每个 token / rule / adaptation / narrative 必须携带真实 `Lx[-Ly]` 与逐字 quote。
占位来源、越界行号、quote 与原文不符、示例数据臆造的主题条件会被拒绝或降级。
带 Clarity/Accessibility/Consistency/Integrity 等原则标签的抽象宣言即使被模型标成
must，也会重分类到 L3；质量门至少要求 2 条可执行 L1/L2，避免“规则数量足够
但全部无 ops”的 persona 被误判为可用。
同一逐字证据已有确定性可执行映射时，模型重复生成的自然语言版本会被去重，避免同一
规范同时出现 applied 与 suggested。需要 `data_role`/`audience` 但读图阶段缺少对应
事实的慢道项会先验驳回；“辅助数据用中性色”不会退化成整图改色。

**落盘形态（对齐手工范例 `data/bbc-persona.yaml` / `data/economist-persona.yaml`）**：

- 主文件 `*-persona.yaml` **仅含** `institution` / `applicability` /
  `L1_signature` / `L2_adaptations` / `L3_narrative`（含 philosophy、stories、
  exemplars）；**不含** `unmapped_requirements` / `evidence_catalog` /
  `parser_provenance`。
- 完整审计统计写入同目录 sidecar `*-parser-audit.yaml`，供研究 provenance 复盘，
  不进入机构人格三层正文，也不被注册表当作 persona 装载。

## 2. 表示：persona 的计算职责（三层各司其职）

persona.yaml（`data/*-persona.yaml`，自定义的存 `backend/storage/personas/`）装载后按层编译：

- **L1 气质签名**（tokens + 无条件规则）
  - tokens → 令牌索引（叶子名 / 点路径双查），快道"令牌直注"的取值来源；
  - `check: programmatic` 规则 → 绑定检测器（`detectors.py`，按 rule id 注册），
    既做拍2违规检测，也做拍4编译后的**不变量核验**；
  - `check: llm` 规则 → 无法程序判定，拍2自动列入升级清单。
- **L2 特征适应**（when→then 条件规范）
  - `when` → 结构化条件求值器（`conditions.py`）：数值比较、受控词槽可快判；
    语义条件（intent / data_role / 自然语言取值）返回 unknown → 升级；
  - `then` → 动作编译器（`actions.py::compile_then`）：编译为可序列化 ops
    （set_mark_color / highlight_category / set_background / merge_config …），
    颜色与字号一律经令牌索引解析为具体值，**不经 LLM 转写**；对 `vconcat`/`layer`
    等复合视图，mark/encoding 类 op 落到几何 unit（禁止在根上创建无 type 的 mark）；
  - 超出单图 spec 的目标（版式 grid.gap、图型迁移 chart.type、多图一致性）
    编译为"建议"（suggested，无 ops）。
- **L3 叙事认同**（哲学 + 理由故事）
  - 慢道裁决（拍3）的担保语料与系统提示；
  - 每处修改标签的解释语言（story 字段 → 前端 reason 展示）；
  - derived 推导提案的依据（如 canvas 令牌 + 视觉和谐哲学 → 图底色，降置信）。

## 3. 推理：四拍状态机（每个 advisor agent 每次运行固定走完）

```
uploaded spec ─→ [intake·LLM角色+extract→emit] ─→ working_spec + communication_goal
                      live:LLM / mock:启发式
         ─→ [拍1 慢道·读图立意] ─→ [拍2 快道·规范检测] ─→ [拍3 慢道·溯源裁决] ─→ [拍4 快道·编译核验] ─→ proposal
            LLM/启发式              纯代码                  LLM/启发式              纯代码
```

- **拍前 intake（extract→emit，非原地补丁）**：advisor 收到上传 Vega-Lite 后、进四拍与
  `extract_facts` 之前，**live 先用 LLM 裁决各层角色**，再抽取并组装干净工作副本。
  **尽量不丢内容**：保留主几何、overlay、annotation 标注与 grid；title/source 提升到根；
  **仅自绘假轴（`drawn_axis`）默认丢弃**；剥绝对图例/轴坐标，统一标准 title/axis/legend。
  mock 或 LLM 失败时启发式回退。简单标准 unit 可 passthrough。写入
  `facts.spec_rebuild`（含 `role_source`）；有改动时 proposal 附 `prepared_spec`。
  `original_spec` 仍为上传原稿；四拍 ops 只作用在 working 上。
- **拍1 读图立意**（slow）：装配 `advisor_briefing` 后，LLM 阅读 **`chart_slice`
  （紧凑图摘要，非完整 VL）+ facts**，产出 **Decision IR**
  （data_topic / intent / emphasis_target / **emphasis_field** /
  **emphasis_mechanism** / coloring_mode / organization / summary）。
  强调绑定由 LLM 据 slice 域样本判定，程序校验后按 mechanism 编译
  （多序列 `set_color_range` / 字面双色 accent / 单序列 `highlight_category`），
  **禁止**用 `category_field` 硬猜 VL 字段。
  合法 `coloring_mode` 以 LLM 判断为准；仅非法枚举才回退启发式。写入
  `facts.decision_ir` / `facts.chart_slice`。**复合图**：拍前 rebuild 优先 LLM 层角色；
  passthrough 时可补一轮。随后 `user_intent.py` 归类 communication / edit / mixed / other
  （意图分析亦附 chart_slice）。改件类在 action space + 令牌内编译为 `user` 层候选。
  **改图仍只由程序令牌 ops 完成，LLM 不写 VL / 不发明 hex。**
- **拍2 规范检测**（fast）：L1 检测器直判 + L2 条件求值。三种出口：
  - 直判候选（violated / matched，附 ops）；
  - **升级清单**（check:llm、语义条件、需语义槽位、any-of 待择一）→ 交拍3；
  - 核验清单（verify_only，如无障碍对比度）→ 交拍4 终检。
  **配色原则（不仅「色在板内」）**：拍1 产出 `coloring_mode`
  （uniform / paired / categorical / highlight）。L1 色板检测（`s-house-palette` /
  `s-palette-blues`）在成员合规但未落实分配原则时仍判违规并生成按模式的 ops；
  L2 配色歧义携带 `color_alternatives`；若仍无配色修复，派生 `d-color-assignment`
  升级慢道。原则：uniform 收束机构主色；paired 双色对；categorical 按指南色板**序列**。
- **拍3 溯源裁决**（slow）：对升级清单逐项三分支——
  - 明文担保（src 有直接依据且情境吻合）→ 采纳（high/medium）；
  - 哲学可推导 → derived 采纳、**降置信**（low）；
  - 无担保 → **驳回不改**，驳回列表随 proposal 返回（留痕）。
  含 `color_alternatives` 时按 `coloring_choice`（live）或 `facts.coloring_mode`（mock）
  选取已解析 ops，禁止发明新 hex。升级项与 payload 附带 **`chart_slice`**，供 LLM
  对照 encoding.color / colors_effective 做判断，而非仅机械看 rule 文本。
  `user_intent_analysis` 只用于情境吻合与规则选择，**不得覆盖指南证据或扩大 action space**；
  与 slots 一致的 communication 项在 mock/live 中提高 adopt 倾向。用户与 L1 never 冲突项并入 rejected。
  **可选视觉审图（同拍、不增拓扑）**：慢道 live 且 `VIZGUIDE_VISION_MODE` 非 off 时，
  后端用 `vl-convert` 将 **working spec** 渲成 PNG（无需前端传图；
  `context.preview_image` 仅作覆盖），再调多模态模型（默认 `gpt-4o-mini`）对照
  **L3 哲学** 检查重叠 / 成对色差观感 / 留白等；输入附带 **`layout_slice`**
  （轴朝向/绝对键等结构 IR，非完整 VL）。产出 `v-*` L3-derived，
  preferred_actions 由程序接地为令牌 ops 或 suggested；**不发明 hex**。
  **结构布局问题**（如孤儿水平 y 轴标题）由 `layout_audit` 程序检测并落地，
  vision 跳过时仍执行；感知类问题才依赖看图。快照仅留 `preview_image_meta`。
  落地加固：可执行 op 与 soft 建议拆开；重叠按 facts 分流 thin/remove；
  已有多色/高亮时不强行 `recolor_uniform`；`set_mark_color` 保留 condition 强调。
- **拍4 编译执行与校验**（fast）：先重放 `user` 层可执行 ops，再机构层。**同节点编排**：
  配色/改型等冲突键只保留一条，优先级 **慢道采纳（拍3）> 快道候选（拍2）**；被覆盖项
  降为 suggested 并注明原因。执行用 `apply_ops_with_effect`：**仅当 working spec 相对执行前
  有实际 diff 才标 `applied`**；静默无落点或已是目标态 → `suggested`（杜绝虚假落地）。
  随后 L1 不变量核验，并重抽 facts 校验 `coloring_mode` 是否落实（`d-coloring-mode`）。
  改色写 `fill`/`stroke`（主数据层），`merge_config` 网格色同步
  自绘 rule，`set_font_sizes` 剥除通道字体并同步根 title / 标题 text 层；`set_title_text` /
  `set_source_note` 落地 sentence case、要点式标题、副标题去重与 Source 追加（不擦描述性
  副标题）；柱上数值标签保留。**用户意图 vs persona 冲突**：若用户已明确改型
  （`set_mark_type`），同 action 的机构项不再 applied，降为 suggested 保留展示，
  避免 pie/line 等互相踩坏 encoding；用户意图优先保证可渲染输出。用户 pie 时锁
  `set_mark_color`，并写入 `{palette.categorical}` 的 `color.range`（避免拍2 在改型前
  `color_count≤1` 误套 primary 单色）。明确
  `set/override chart.type` 与用户受控改型可 `set_mark_type`（IBM 可映射别名含
  area/boxplot/bubble/donut/heatmap/histogram/lollipop/stacked* 等；radar 等仍建议）；
  `prefer chart.type` 默认仍为建议（`VIZGUIDE_PREFER_MODE=suggest`）；设为 `apply` 时受控
  mark 落地，但不得覆盖已锁定的用户改型。`d-canvas-bg` 对默认白底亦可覆盖。

### live / mock 双模式 ≠ 快慢道

live/mock 只是拍1、拍3（慢道）的**实现后备**：配置 OpenAI 兼容 API（`OPENAI_API_KEY`）
即真实 LLM；未配置时用确定性启发式顶替（关键词主题、意图映射、语义门 + 保守驳回），
保证离线可端到端运行、测试可复现。四拍拓扑在两种模式下完全一致。论文实验使用 live。

### 状态与路由（run 生命周期）

`POST /api/advisor/run` → RunStore 建 run → 每个 persona 一个 asyncio task：
`pending → reading → detecting → adjudicating → compiling → done|error`
前端按状态轮询映射进度环；`run_id` 为本地时间精确到分钟（`YYYYMMDD-HHMM`，
同分钟冲突加 `-2`…）；run 完成后快照落盘 `backend/storage/runs/{run_id}.json`
（request / 各 agent proposal / 逐拍 trace），作为研究 provenance。
快照**第一行**为单行 JSON：`llm_api_mock_fallback`（是否因 LLM API 故障降级
mock；配置即为 mock 时为 false）；第二行起为完整正文（含 `llm_api_status`）。
同目录另存 `storage/runs/{run_id}.llm.jsonl`：该次运行全部 LLM API 的
system/user/`raw` 原文/`parsed`/error（图片 base64 省略）。

## 4. 方案输出（proposal 契约要点）

每个 agent 返回：`modified_spec`（可直接渲染）+ `changes[]`（每处修改：label /
reason / prompt / layer / strength / confidence / **warrant**{src, story, derived,
source_file} / ops / status applied|suggested）+ `rejected[]`（驳回留痕）+
`invariants[]`（L1 终检）+ `trace[]`（四拍耗时与摘要）。

## 5. 组合与交互（Composer）

用户跨机构采纳 changes → `POST /api/design/apply`：按采纳顺序确定性重放 ops
（无 LLM）。v1 走令牌动词表；v2 的 `compose_component` 按 `spec_paths` 从各机构
候选图取值并写入源图（跨机构借色/借标题是路径级覆盖，不是整图替换）。用户在
聊天框额外编辑的自由文本，live 模式下交 LLM 微调并校验输出仍为合法 spec，
mock 模式跳过并注记。

## 6. 与论文创新点的对应

### 6.1 v1 引擎（编译执行）

- 表示创新点：persona 不是提示词而是**可编译的知识模型**——三层分别编译为
  检测器/不变量、条件求值+动作编译、裁决担保+解释语言；三层评估钩子
  （L1 可辨识度 / L2 情境合宜 / L3 理由忠实度）见 persona.yaml 尾注。
- 推理创新点：default-intervened 的可验证实现——结构化条件快判、判不了升级；
  裁决三分支且驳回是一等输出；令牌直注不经 LLM 转写；编译后 L1 不变量核验。
- 消融支持：拍与拍解耦——去掉快道（全部升级慢道）≈ 整份指南模板套用 baseline；
  去掉慢道（只执行快道直判）≈ 纯规则 baseline；trace 支撑逐拍归因。

### 6.2 v2 引擎（契约核验）——知识编译为**可验证契约**

v1 把「执行」与「校验」都绑在 `then` 编译上，表达上限因此等于动作词汇表：
结构性改动（注释层、轴组织、layer 重排）无法表达，机构人格显得僵硬。
v2 只放开执行、保留校验，主张相应从"知识编译为可执行操作"改为
**"知识编译为可验证契约"**：

- 表示创新点：三层知识编译为**绑定契约**——L1 由检测器在源图上判定合规状态
  （`already_satisfied` / `violated_by_source_chart` / `not_machine_checkable`），
  L2 由 `eval_when` 三态求值分为 `triggered` / `requires_persona_judgment` /
  `inactive`，L3 作为构图与理由的最高优先级依据。契约是带证据的约束，
  不是提示词里的规则罗列。
- 推理创新点：**生成自由 + 核验强制**。拍3 LLM 拥有完整 Vega-Lite 设计权；
  拍4 用**同一批检测器**在生成图上重跑不变量核验，仍违规且带可编译 `then` 的
  规则由令牌 ops 确定性修补（安全闸门失败即回滚）。令牌直注与编译后核验两项
  性质因此保留，动作编译器从"唯一执行手段"降为"兜底修补器"。
- 归因创新点：commitment manifest **由程序对着真实 diff 核验**——每条声明必须
  指向候选 spec 中真实存在、且相对原图确有变化的叶子路径，组件归属唯一、
  路径不重叠、不得把"保持不变"伪装成修改（`_check_commitments`）。这比 v1 由
  LLM 自述 warrant 的归因更硬；快道修补另生成**程序署名**的 commitment，
  变更记录不把程序改动算作模型决策。
- 消融支持：`VIZGUIDE_V2_L1_ENFORCEMENT=patch|report|off` 三档直接对照
  「契约是否可验证」；v1/v2 双引擎并存则对照「封闭动作空间 vs 自由生成」。
